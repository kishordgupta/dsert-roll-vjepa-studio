# DSERT-RoLL V-JEPA Studio

A local research interface for **prompt-controlled sensor augmentation with V-JEPA 2.1 representation analysis**.

> **Clarification (2026-09-25): V-JEPA did not generate the demo video or sensor measurements.** Custom Python code creates augmented versions of existing DSERT-RoLL recordings. The pretrained V-JEPA encoder extracts features from their rendered visual sequences for comparison. The original goal of a prompt producing a new scene, video and corresponding sensor measurements through V-JEPA is **not implemented**.

## What each component actually does

| Component | Actual role |
| --- | --- |
| Prompt parser | Maps supported keywords to predefined weather and lighting settings. No text prompt is passed into V-JEPA. |
| Augmentation code | Modifies recorded RGB, event, thermal, LiDAR and radar data using programmed, seeded transformations. It writes the video and native sensor files. |
| V-JEPA 2.1 encoder | Extracts visual token features from the original and augmented sequences. The project pools them into a 768-dimensional embedding per stream. |
| Comparison code | Normalizes and combines embeddings and computes cosine distances. These scores describe feature changes. |
| Validation code | Checks file formats, timestamps, finite values and output integrity. These checks do not establish physical realism. |

The actual data flow is:

```text
Supported prompt + recorded DSERT-RoLL data + strength + seed
    -> keyword settings
    -> sensor-specific augmentation code
    -> augmented native arrays, rendered views and video files

Original and augmented rendered views
    -> pretrained V-JEPA encoder
    -> pooled embeddings
    -> cosine-distance comparison
```

In [engine.py](prompt-studio/engine.py), the model loader returns an encoder and a predictor, but the code explicitly runs `del predictor`. This project uses **encoder inference only**. It does not train or fine-tune V-JEPA, perform a learned future-state rollout, or include a learned decoder that converts features into pixels or sensor measurements. The augmentation content does not depend on the encoder's output; the full application workflow still loads the encoder to complete its analysis.

The UI and existing demo assets use labels such as **Generate**, **generated** and **synthetic**. Here those labels mean **procedurally augmented files derived from a source recording**, not content generated by V-JEPA. New files do not imply a new world, route or set of independently simulated sensor observations.

## What the prompt does

Choose a source recording, enter a supported weather or lighting prompt, and set strength and seed. The keyword parser selects fixed effects in the augmentation code. Scene geometry, routes, object identities, frame timestamps and recorded poses remain from the source dataset. No new GPS/IMU trajectories are synthesized.

Supported effects: fog, rain, snow, night and warm light, including combinations such as **Heavy rain at night**. **Original** produces an unmodified reference condition. This is a command interface for predefined effects, not open-ended text-to-video generation. Unsupported object or route prompts are rejected.

## Quick start

Tested on Ubuntu 24.04 under WSL, Python 3.11, PyTorch 2.5.1 with CUDA 12.1, and one Quadro RTX 5000 GPU with 16 GB VRAM. The current model code requires CUDA. GPU indices are selectable; multiple GPUs are not combined.

1. Clone the public repository: `git clone https://github.com/kishordgupta/dsert-roll-vjepa-studio.git`, then `cd dsert-roll-vjepa-studio`. No GitHub sign-in is required to clone it.
2. Install Python 3.11 with venv support, Git and FFmpeg. On Ubuntu: `sudo apt-get install ffmpeg`.
3. Run `bash scripts/setup.sh`. This creates `.venv311`, installs dependencies, checks out the pinned V-JEPA source, applies the official-checkpoint URL patch, and downloads selected dataset subsets and the checkpoint. Allow several GB of disk and network traffic.
4. Run `CUDA_VISIBLE_DEVICES=0 bash prompt-studio/start.sh` (use `1` for the previously tested GPU on the remote workstation).
5. Open **http://127.0.0.1:8765** on the same computer.

The server binds to localhost and accepts one augmentation-and-analysis job at a time. Initial model loading takes longer than subsequent jobs. Logs are in `prompt-studio/server.log`.

## Demo

Choose **Clear daylight**, prompt **Heavy rain at night**, strength **0.7**, seed **42**. The word heavy scales effective strength to 0.875. The verified run produced 48 frames at approximately 9.987 fps, covering 4.806 seconds. Augmentation, rendering, validation and feature analysis took 150.24 seconds on the tested GPU.

The augmentation code wrote **432 primary sensor files**, containing **88,286,126 events** and **3,828,874 points** after transformation. These totals include data retained or perturbed from the recording as well as any procedurally added samples; they are not counts of measurements generated by V-JEPA. All 48 frames in all nine streams changed. The native sensor ZIP is about 586 MB and stays local. Small example videos and verification summaries are in [docs/demo](docs/demo).

## Finding augmented data and model features

Each run is under `prompt-studio/jobs/<job-id>/`:

| Output | Contents |
| --- | --- |
| `video.mp4` | Camera video rendered from procedurally augmented recorded frames |
| `comparison.mp4` | Recorded source and augmented version side by side |
| `synthetic_sensors.mp4` | Rendered preview of all nine augmented streams |
| `sensor_data.zip` | Augmented native sensor files, metadata and source provenance |
| `sensor_data/` | Uncompressed augmented native outputs |
| `embeddings.npz` | Pooled V-JEPA features of original and augmented visual sequences |
| `metrics.json` | Parameters, timing and representation distances computed by project code |
| `validation.json` | Schema, timestamp and integrity validation |

Use the UI sensor ZIP download for native data. Preview videos are visualizations, not replacements for arrays. V-JEPA receives rendered visual sequences of each stream separately; raw event arrays, LiDAR points and radar measurements are not fed directly into a pretrained multimodal sensor model.

## Sensor semantics

| Family | Streams | Native output and transformation |
| --- | --- | --- |
| RGB | Left, right | 960 x 600 PNG; lighting, haze, precipitation; scaled intrinsics |
| Events | Left, right | uint32 NPZ [x, y, polarity, source-local timestamp]; thinning and synthetic events |
| Thermal | Left, right | Non-radiometric PNG intensities; contrast and weather variation |
| LiDAR | Livox, Ouster | Structured NPY points; radial noise, dropout, attenuation, backscatter |
| Radar | One | Structured NPY points; range, power and Doppler perturbations |

Frame timestamps and recorded poses are retained. Event clock units are not independently calibrated. Thermal outputs are display intensities, not temperatures. Radar numeric units retain source conventions. These are sensor-specific research augmentations, not a physically calibrated shared-world simulator. A common prompt and synchronized timestamps do not establish physical consistency across the sensors. No new GPS/IMU trajectories are synthesized.

## What would be needed for new-scene generation

Producing a new scene from arbitrary text, together with consistent video and sensor measurements, would require an additional generative system or a calibrated simulator and suitable sensor models. That component is absent from this repository. V-JEPA feature extraction can support analysis, but it does not supply that missing generation capability.

## Model and data provenance

- [Meta V-JEPA 2/2.1](https://github.com/facebookresearch/vjepa2), commit `204698b45b3712590f06245fbfba32d3be539812`.
- Backbone: `vjepa2_1_vit_base_384`, distilled ViT-B; 16 sampled frames per stream and 768-dimensional embeddings.
- [DSERT-RoLL dataset](https://huggingface.co/datasets/jeongyh98/DSERT-RoLL), with revisions and sequence selections in `multisensor/selection.json` and `multisensor/synthetic-selection.json`.
- [Official dataset code](https://github.com/jeongyh98/DSERT-RoLL-Dataset).
- Model and dataset are subject to upstream licenses. Weights and recordings download separately. The selected public files use public URLs; no Hugging Face token is embedded.

## Code map

- `prompt-studio/catalog.py`: supported prompt grammar and recording catalog.
- `prompt-studio/sensor_synthesis.py`: native transformations and provenance.
- `prompt-studio/multisensor_pipeline.py`: augmentation orchestration, embedding comparison and validation.
- `prompt-studio/engine.py`: rendering and V-JEPA feature extraction.
- `prompt-studio/server.py`, `static/`: localhost API and web interface.
- `multisensor/`: acquisition, schema handling, rendering and evaluation.
- `scripts/setup.sh`, `scripts/prepare_data.py`: portable installation.

## Validation and security

Run `.venv311/bin/python prompt-studio/test_sensor_models.py` for deterministic sensor checks. The verified full demo checked every primary file, source hashes, timestamps, full FFmpeg video decoding and ZIP CRC integrity. Representation distances measure feature changes. They do not validate physical realism, cross-sensor consistency, weather robustness or downstream accuracy. No downstream benchmark demonstrating those properties is included in this experiment.

Credentials, SSH keys, environment files, caches, weights, full datasets, jobs and logs are excluded from this repository. Store authentication outside the checkout. The temporary publishing deploy key is removed after upload verification.

After a completed run, verify the UI output bindings with `.venv311/bin/python prompt-studio/verify_sensor_app.py <job-id>`.
